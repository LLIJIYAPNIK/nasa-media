# TZ-web.md — веб-интерфейс, этап 1: главная страница

## Цель

Начать `presentation/web`, о котором CLAUDE.md давно говорит как о «следующем
этапе» ("Веб-интерфейс доступа ко всем API NASA... часть того же
репозитория `nasa-media`"). Этот заход — только главная страница
(лендинг). Остальные разделы (APOD, EPIC, Астероиды, Космическая погода,
События Земли, Итоги недели) получают свои страницы позже, каждая — свой
`TZ-web-<раздел>.md` по той же схеме; здесь их вёрстка не описывается,
только заглушка-роут, чтобы навигация не вела в никуда.

## Источник дизайна

Дизайн главной страницы уже сделан в Claude Design (5 концептов, из них
выбран и доработан один):

- Проект: `https://claude.ai/design/p/cba4ea58-066d-4099-98ad-702fa136a2f2?file=Главная+nasa-media.dc.html`
- Импортировать через MCP `claude_design` (`https://api.anthropic.com/v1/design/mcp`,
  авторизация `/design-login`) — это инструмент Claude Code, он читает исходный
  `.dc.html`/`support.js` файл проекта напрямую и должен быть использован
  **как первый шаг реализации**, до вёрстки. Держать файлы дизайна открытыми
  весь заход — они единственный источник точных значений (цвета, отступы,
  радиусы, blur), эта ТЗ их не задаёт числами.
- Реализовать нужно вариант **4b** — "Боковая иконочная навигация · Земля
  справа": вертикальная стеклянная иконочная навигация слева, крупная
  вращающаяся 3D-Земля справа (85–90% экрана, ночная сторона с городскими
  огнями), заголовок "Данные NASA — ближе, чем кажутся", бейдж "Данные NASA ·
  обновляются каждую минуту", кнопки "Исследовать данные" / "Итоги недели",
  далее — единый вертикальный блок ежедневной статистики на стеклянных
  карточках. Остальные 4 концепта (1a–3a и т.п.) в проекте остаются как
  референс истории выбора, реализовывать их не нужно.
- `.dc.html`/`support.js` — формат внутреннего canvas-рантайма Claude Design
  (см. содержимое `support.js`: `dc-runtime`, `parseDcDocument` и т.п.), не
  предназначен для продакшена как есть. Из него переносится ВИЗУАЛЬНЫЙ ЯЗЫК
  (макет, порядок секций, содержимое блоков, состояния интерактивных
  элементов) в стек ниже — не копируется код рантайма.
- Подтверждённая навигация (7 пунктов, все реализованы в боте, кроме
  собственно веб-страниц под них): Главная, APOD, EPIC, Астероиды, Погода
  (космическая), События (Земли), Итоги недели.

## Выбор стека (обоснование)

Технических указаний по вебу в CLAUDE.md пока не было — ниже решение,
привязанное к тому, что уже есть в проекте, а не выбранное абстрактно.

- **Backend — FastAPI**, новый пакет `presentation/web/`, отдельный процесс
  от бота (`uv run uvicorn presentation.web.app:app`), но тот же
  репозиторий и тот же `domain`/`application`/`infrastructure` — ровно то,
  что и планировалось в CLAUDE.md ("presentation/web... подключался к тем же
  application-сервисам, не трогая и не дублируя domain/application/
  infrastructure"). Отдельный процесс, а не встраивание в `aiogram`-цикл:
  `dp.start_polling` и ASGI-сервер — разные event loop-модели, смешивать их в
  одном процессе не нужно и не даёт никакой выгоды. Деплой двух процессов
  (бот + веб) — вопрос README/инфраструктуры, не этой ТЗ (см. «Вне рамок»).
- **Шаблоны — Jinja2 (входит в FastAPI-стек), не React/SPA.** Совпадает с
  тем, как устроен фронтенд сайта-компаньона автора (a-kulebyakin.ru:
  "HTML + CSS + минимум vanilla JS. Никаких React и тяжёлых
  SPA-фреймворков") — тот же вкус проекта, к тому же для одной главной
  страницы с точечной интерактивностью (обновление статистики, модалка)
  SPA-фреймворк был бы избыточен.
- **HTTP-клиент для NASA API на веб-стороне — тот же `aiohttp.ClientSession`**,
  что уже используют `infrastructure/nasa/*_client.py` — не заводим `httpx`
  ради веба, инфраструктурные клиенты уже принимают сессию в конструктор и
  никак не завязаны на aiogram.
- **3D-Земля — Three.js** (ESM-сборка с CDN, без сборщика/бандлера — верно
  вписывается в "минимум vanilla JS"). Ассеты уже лежат в репозитории
  (некоммиченные, в корне): `c7n8gttq5hxc-Earth/Maps/Color Map.jpg`,
  `Night Lights.jpg`, `Bump.jpg`, `Clouds.png`, `Spec Mask.png` — набор карт
  на текстурированную сферу с ночной стороной, ровно под задуманный в 4b
  вид. **Происхождение и лицензия этого набора не задокументированы** (папка
  похожа на сторонний ассет-пак с 3D-моделью — `earth.blend`/`earth.obj`/
  `earth.3ds` — не на официальный NASA Visible Earth/Blue Marble) — перед
  коммитом текстур в публичный репозиторий свериться с автором (пользователем),
  откуда они взялись, и при отсутствии ясной свободной лицензии заменить на
  открытые снимки NASA Visible Earth/Blue Marble (public domain, как и весь
  остальной NASA-контент проекта, см. `TZ-copyright.md`). Использовать нужно
  только плоские текстуры (`Maps/*`), 3D-модель (`.blend`/`.obj`/`.3ds`)
  Three.js не нужна — сфера с текстурой строится геометрией `SphereGeometry`.
- **Мобильный/слабый рендер — CSS-fallback, не видео.** Если `WebGL`
  недоступен или `matchMedia('(prefers-reduced-motion: reduce)')` истинно —
  показывать статичную текстуру Земли с медленной CSS-анимацией
  `background-position` вместо WebGL-канваса: даёт то же ощущение "медленного
  вращения", не тянет вес видеофайла и не требует второго набора ассетов.
  `prefers-reduced-motion` уважается в любом случае (в дизайн-брифе это не
  обсуждалось явно, но это стандартное веб-требование доступности, разумно
  добавить сразу, а не отдельным проходом).
- **Данные для страницы — НЕ через `application/media`/`admin-chat`-кеш.**
  Существующий цикл (`DeliverMediaForDate`, `AdminChatGateway`, `*Repository`)
  — про "закешировать и переслать в конкретный Telegram-чат", а веб-странице
  нужно "показать сегодняшние данные всем посетителям как JSON" — разные
  задачи с разной формой результата. Новый read-only слой
  `application/web/` обращается к тем же портам источников
  (`SpaceWeatherClient`, `NearEarthObjectClient`, `NaturalEventClient` из
  `application/digest/ports.py` — уже определены, переиспользуются как есть)
  и к тем же чистым доменным функциям выбора (`pick_significant_space_weather`,
  `pick_closest_asteroid`, `pick_latest_earth_event` из
  `domain/digest/digest_text.py`), но НЕ переиспользует
  `build_digest_lines`/`_format_*` — те собирают текст с эмодзи под
  Telegram-сообщение, а не структурированные данные под JSON/HTML. Дублирования
  в этом нет: главное (сеть + выбор "какое событие показать") переиспользуется,
  расходится только последний шаг форматирования — ровно так же, как сейчас
  расходятся `build_digest_lines` (для чата) и генерация карточки
  (`card_builder.py`) для того же дайджеста.
- **`ApodProvider.fetch()` требует небольшого рефакторинга, не копирования.**
  Сейчас он одним методом делает три вещи: HTTP-запрос к NASA, перевод через
  `Translator`, сборку Telegram-подписи (`build_apod_caption`) — и отдаёт уже
  готовый `SinglePhotoPayload` с одной строкой `caption`, из которой веб не
  сможет достать заголовок/описание/copyright по отдельности. Выделить
  `ApodClient.fetch_raw(day) -> ApodData` (новый dataclass:
  `title, explanation, copyright, image_url` — уже переведённые через тот же
  `Translator`) в `infrastructure/nasa/apod_client.py`; `ApodProvider.fetch()`
  (для бота) становится тонкой обёрткой: вызывает `fetch_raw`, затем
  `build_apod_caption(...)` из результата. `application/web` вызывает тот же
  `fetch_raw` напрямую. Без этого разделения пришлось бы либо парсить
  строку `caption` (хрупко), либо второй раз писать HTTP+перевод (дублирование).

## Ежедневная статистика — что именно показываем

Дизайн-бриф просил "не выдуманные цифры" — ниже привязка каждой карточки к
реальному источнику, без фантазий:

- **APOD.** Не "стрик бота" (у бота нет смысла считать её отдельно — кеш
  просто есть/нет на дату) — вместо этого настоящий факт: NASA публикует
  APOD ежедневно без перерыва с **16 июня 1995 года**
  (`apod.nasa.gov/apod/ap950616.html`, первый выпуск "Neutron Star Earth").
  Карточка показывает "день №{N} с 1995 года" — `N = (сегодня -
  date(1995, 6, 16)).days`, чистая функция в `domain/media/apod_day_count.py`
  (рядом с `apod_caption.py` — это знание про APOD как понятие, не "про веб":
  домен не должен знать о presentation-поверхностях, см. «Инженерные
  принципы» в CLAUDE.md), дата опоры — константа с комментарием на источник.
  Клик — модалка с сегодняшним APOD (заголовок, описание, картинка,
  copyright, если есть).
- **Астероид.** Ближайший на сегодня — `pick_closest_asteroid` над
  `NearEarthObjectClient.fetch_for_day(today)` (тот же порт и клиент, что и
  дайджест бота). Карточка — имя + дистанция в лунных расстояниях; клик —
  модалка с полным диапазоном диаметра (и бытовым сравнением через уже
  существующую `compare_to_familiar_object`, `TZ-asteroid-comparison.md`),
  скоростью нет в текущем `AsteroidHighlight` — **не показывать то, чего нет
  в доменной модели**; при желании добавить позже отдельной небольшой ТЗ,
  не расширять модель по ходу этой.
- **Космическая погода.** `pick_significant_space_weather` над
  `SpaceWeatherClient.fetch_for_day(today)`. Карточка — тип события или
  "спокойно"; клик — модалка с типом, временем (`issued_at`) и обычной
  фразой (данных больше, чем в `SpaceWeatherHighlight`, сейчас нет — не
  дополнять модель, честно показываем то, что есть).
- **Событие Земли.** `pick_latest_earth_event` над
  `NaturalEventClient.fetch_recent()`. Карточка — заголовок + категория;
  клик — модалка с тем же (`title`, `category`, `event_date`) — та же
  оговорка про честность данных.

Если по какому-то из четырёх пунктов на сегодня нечего показать (например,
космос спокоен, событий на Земле нет) — карточка всё равно кликабельна,
модалка объясняет это человеческим языком ("Заметных вспышек сегодня нет"),
не показывает пустое окно.

## Модалка по клику (новое требование к дизайну)

В дизайне 4b карточки статистики были статичным блоком — добавляется
интерактивность:

- Каждая карточка — `<button>` (не `<div>` с `onclick`, чтобы работать с
  клавиатуры и читалками экрана из коробки), `data-kind="apod|asteroid|
  space-weather|earth-event"`.
- Модалка — нативный `<dialog>` (встроенный фокус-трэп и backdrop в
  современных браузерах, без сторонней библиотеки): `dialog.showModal()`,
  закрытие по Esc/клику на backdrop/кнопке закрытия — всё это `<dialog>` даёт
  бесплатно.
- Контент модалки не встраивается в HTML главной страницы заранее (было бы
  тяжелее и требовало бы всегда переводить/собирать все 4 полных описания,
  даже если посетитель ни разу не кликнет) — подгружается лениво через
  `fetch('/api/homepage/details/{kind}')` при первом клике по карточке этого
  типа, дальше кешируется на стороне клиента (`Map` в JS) на время жизни
  страницы, повторный клик не бьёт по сети снова.
- Отдельный `/api/homepage/details/{kind}` (не общий `/api/homepage/snapshot`
  сразу со всеми деталями), потому что сводный снапшот обновляется каждую
  минуту для всех посетителей сразу (см. ниже) и должен быть лёгким — полное
  описание APOD/астероида не нужно гонять в каждом периодическом опросе.

## Роуты

- `GET /` — рендерит страницу (Jinja2): нав-рейл, hero, `<canvas>`-точка
  монтирования Three.js, блок статистики. Значения статистики
  сервер-рендерятся в HTML при первом ответе (быстрая отрисовка, страница
  осмысленна даже без JS) — не только через JS после загрузки.
- `GET /api/homepage/snapshot` — JSON с теми же 4 краткими значениями, что и
  в HTML — фронтенд перезапрашивает раз в 60 секунд, чтобы бейдж "обновляются
  каждую минуту" не был декорацией.
- `GET /api/homepage/details/{kind}` — JSON с полным содержимым модалки для
  одного из 4 `kind` (см. выше); `404` с понятным телом, если `kind`
  неизвестен.
- `GET /apod`, `/epic`, `/asteroids`, `/space-weather`, `/earth-events`,
  `/weekly-highlights` — временные заглушки: общий шаблон `placeholder.html`
  (та же навигация/шапка, текст "Раздел в разработке — скоро здесь будет
  {название}"), не `404` и не пустая ссылка `href="#"` — так навигация из
  4b рабочая уже сейчас, без обмана и без разработки самих разделов.

## Кэширование NASA-запросов на веб-стороне

Один и тот же снапшот не должен вызывать 4 обращения к NASA API на каждый
заход посетителя — при заметной посещаемости это и медленно, и упирается в
квоту `NASA_API_KEY`. Простой in-memory TTL-кэш (не Redis — не нужен на
таком масштабе, см. принцип "не усложнять раньше времени" в CLAUDE.md):
`infrastructure/web/snapshot_cache.py`, ключ — дата, время жизни — 5 минут
(достаточно свежо для бейджа "каждую минуту", который относится к тому, что
*модель данных* поминутная, а не что каждый запрос обязан бить в NASA
живьём). Если проект вырастет — заменяется на Redis без изменения
`application`/`domain`, только реализация порта в `infrastructure`.

## Что осознанно вне рамок

- Вёрстка страниц APOD/EPIC/Астероиды/Погода/События/Итоги недели — заглушка
  в этом заходе, полноценная реализация каждой — отдельная `TZ-web-<раздел>.md`
  по готовности.
- Карта/геолокация для событий Земли — координаты не показываем вообще в
  этом заходе (в дизайне 4b их не было и в дайджесте бота их не показывают),
  не расширяем модель ради этого.
- WebSocket/SSE — поллинг раз в 60 секунд достаточен для тэглайна
  "обновляются каждую минуту", пуш не нужен.
- Redis/внешний кэш — in-memory TTL достаточно на старте (см. «Кэширование»).
- Деплой веб-процесса (nginx/systemd/докер, TLS, домен) — дополняется в
  README.md отдельно, когда до этого дойдёт очередь, не в этой ТЗ.
- Пиксель-точные значения дизайна (конкретные hex/blur radius/spacing) — не
  фиксируются здесь числами: единственный источник истины — сам файл
  дизайна в Claude Design, читается через `claude_design` MCP непосредственно
  перед вёрсткой.
- Скорость/дополнительные параметры астероида, которых нет в
  `AsteroidHighlight` — не добавляются в доменную модель попутно (см.
  «Ежедневная статистика»).
