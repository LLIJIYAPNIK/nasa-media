# ТЗ: карточка события EONET

## Цель
Расширить карточку события (сейчас показывает только title, категорию и дату) до полноценной, используя все поля Event-объекта из EONET API v3.

## Макет (сверху вниз)
1. Категории — pill-бейджи
2. Заголовок события
3. Статус (открыто/закрыто) + дата
4. Описание
5. Карта с меткой
6. Магнитуда (если есть)
7. Источники и ссылки — внизу

## 1. Описание
- Поле `description` — выводится сразу под заголовком/статусом.
- Если поле пустое (у EONET это частый случай) — либо скрыть блок, либо заглушка "Описание отсутствует".

## 2. Карта с меткой события

**Про EPIC — не подходит.** EPIC даёт снимки всего диска Земли целиком (~2048×2048 px на ~12 700 км), это ~10 км/пиксель без зума на регион. Можно нарисовать точку на снимке глобуса как декоративный элемент, но как рабочую карту с приближением на область события — нет.

**Рекомендуемый источник — NASA GIBS.** EONET сама на него ссылается: `Categories.layers` → Layers API отдаёт `serviceUrl`, `serviceTypeId` (WMS/WMTS), `parameters` для конкретной категории события (например, для severeStorms — соответствующие спутниковые слои). Через WMS/WMTS-запрос можно получить тайл/изображение по bbox.

Если интеграция с GIBS окажется избыточной для MVP — fallback на открытые OSM tiles тем же способом (запрос по bbox → изображение).

**Пайплайн (PIL):**
1. Взять координаты из `geometry` (для Point — сама точка; для трека из нескольких точек — последняя, либо весь трек).
2. Посчитать bbox вокруг точки (± градусов/км, масштаб настраиваемый — см. открытые вопросы).
3. Запросить изображение области у выбранного сервиса по bbox.
4. В PIL: открыть изображение, перевести lon/lat точки в пиксельные координаты (проекция зависит от сервиса — Web Mercator для большинства WMTS/OSM), нарисовать маркер.
5. Если точек несколько (трек урагана) — нарисовать линию пути + маркеры по датам.
6. Закешировать результат по `event.id` (+ дате последней точки), чтобы не перегенерировать при каждом открытии карточки.

## 3. Остальная информация
- **Категории** (`categories`) — вверху карточки, скруглённые pill-бейджи, по одному на категорию, кликабельны (фильтр по категории).
- **Статус** (`closed`) — бейдж "Активно" либо "Завершено · дата".
- **Магнитуда** (`magnitudeValue` + `magnitudeUnit` + `magnitudeDescription`) — отдельной строкой, если поля присутствуют (не у всех событий есть).
- **Источники** (`sources`) — внизу, список ссылок (title → source URL).
- **Ссылка на объект в EONET** (`link`) — тоже внизу, отдельным пунктом.

## Открытые вопросы (закрыты — см. «Решения по неоднозначностям»)
- Где кешировать сгенерированные карты — бэкенд или клиент?
- Дефолтный масштаб карты (bbox) — фиксированный или зависит от типа события (шторм/пожар/вулкан)?
- Нужна ли анимация/полный трек для событий с несколькими точками geometry, или только последняя позиция?

## Живая проверка EONET API (перед реализацией)

Прежде чем парсить, форма ответа проверена живыми запросами (28-29 июля 2026) —
исходное предположение ТЗ («магнитуда — на событии целиком») не подтвердилось:

- `magnitudeValue`/`magnitudeUnit`/`magnitudeDescription` живут **на каждой
  точке `geometry`**, не на событии — у события их просто нет как отдельных
  полей верхнего уровня. Логично: у шторма скорость ветра меняется день ото
  дня, «одна магнитуда на всё событие» не имела бы смысла для трека из
  20+ точек.
- `categories` — массив `{id, title}`, у событий обычно одна категория, но
  бывает больше одной.
- `sources` — массив `{id, url}`, **без отдельного `title`** — `id` (сеть/
  агентство: `"IRWIN"`, `"JTWC"`, `"InciWeb"`) и есть человекочитаемая метка.
- `closed` — `null` (открыто) либо ISO-дата.
- `magnitudeDescription` ни разу не встретилась в живых данных (ни у
  штормов, ни у пожаров) — поле всё равно поддержано в парсинге на случай,
  если NASA когда-нибудь начнёт его отдавать, но пустует для всех текущих
  событий.

## Решения по неоднозначностям (с обоснованием)

- **Магнитуда события = магнитуда последней по дате точки geometry**, не
  общее поле. Раз данные живут на точке — используется та же точка, что уже
  выбрана для маркера на карте и для `event_date` (см.
  `docs/tz/TZ-daily-digest.md`, «EONET: берём одно самое свежее событие»).
  Один источник правды на «текущее состояние события», не два разных выбора
  точки для разных полей карточки.
- **Карта — OpenStreetMap, не GIBS.** ТЗ прямо оставляла этот выбор
  («если интеграция с GIBS окажется избыточной для MVP — fallback на OSM»).
  GIBS требует второго обращения (`Categories` → `Layers API`) и
  согласования WMS/WMTS-параметров **отдельно по каждой категории**
  (severeStorms, wildfires, volcanoes и т.д. отдают разные слои с разными
  `serviceTypeId`) — то есть по сути отдельный маппинг категория → слой,
  который нельзя проверить визуально без живой отладки на реальных
  событиях каждой категории. OSM — один детерминированный XYZ-тайл-запрос
  (`z/x/y`), без дополнительного API-вызова и без per-категорийной логики.
  Требование Tile Usage Policy — идентифицирующий `User-Agent`
  (`infrastructure/web/event_map.py:TILE_USER_AGENT`) и атрибуция
  «© OpenStreetMap contributors» под картой в модалке (добавлена). При
  ощутимом росте трафика — заменить на платный тайл-провайдер или довести
  интеграцию с GIBS; для MVP с файловым кешем на событие это не требуется.
- **Только последняя точка geometry, без полного трека/анимации.** Явно
  вынесено в «вне рамок» ниже — см. обоснование там.
- **Фиксированный bbox (±4° от точки), не зависящий от типа события.**
  Per-категорийный масштаб (шторм крупнее пожара) — отдельная доработка,
  не входит в MVP; вынесено в «вне рамок».
- **Кеш карт — на бэкенде, файловый (не БД/Redis).** `EventMapFileCache`
  (`infrastructure/web/event_map_cache.py`) пишет PNG на диск в
  `var/cache/event-maps/{event.id}_{дата последней точки}.png`. БД/Redis не
  оправданы для маленького числа файлов на бэкенде одного read-only сайта
  (см. принцип «не усложнять раньше времени» в CLAUDE.md, тот же аргумент,
  что и у `SnapshotCache`). Ключ кеша включает дату последней точки —
  если у открытого события за сутки появилась новая точка geometry
  (трек шторма продвинулся), ключ меняется и карта перегенерируется
  автоматически, без явной инвалидации.
- **Ключ карты как отдельный публичный роут, не встроенная в JSON
  base64-картинка.** `GET /api/homepage/earth-event-map/{cache_key}.png`
  отдаёт PNG напрямую (браузер кеширует по URL бесплатно) — `HomepageDetail`
  несёт только `earth_event_map_url` (или `null`, если карта недоступна).
  `cache_key` из пути валидируется regex'ом (`EventMapFileCache._path_for`)
  до обращения к диску — защита от path traversal на пользовательском вводе
  в URL.
- **Недоступность карты не ломает остальную карточку.** Сетевая ошибка при
  скачивании OSM-тайлов (или отсутствие `id`/`geometry` у события) —
  `EventMapBuilder.build()` возвращает `None`, `earth_event_map_url` в ответе
  — `null`, JS просто не рендерит `<img>`. Согласуется с тем, как уже
  устроены остальные карточки главной страницы (`docs/tz/TZ-web.md`:
  «модалка объясняет это человеческим языком, не показывает пустое окно»).
- **Источники — `label` (не `title`), значение = `source.id` из API.** У
  EONET нет отдельного текстового названия источника, только код сети —
  `EventSource(label, url)` называет поле честно под то, что реально
  приходит, не выдаёт код агентства за придуманное «название».
- **Категории кликабельны как ссылки на `/earth-events?category=<id>`,
  без реальной фильтрации.** Сама страница `/earth-events` пока
  заглушка-роут (`docs/tz/TZ-web.md`) — полноценный список событий с
  фильтром по категории появится в её собственном ТЗ. Ссылка на неё уже
  сейчас — минимальная честная реализация «кликабельности» без обмана
  (не `href="#"` и не притворная фильтрация на пустой странице).

```
  /api/homepage/earth-event-map/{cache_key}.png.

presentation/web/static/js/modal.js — renderEarthEvent: пилюли категорий,

  .detail-modal-notice (для заглушки описания).

```

  магнитуда с последней точки, точки без `coordinates` отбрасываются,

## Что реализовано

Полный вертикальный срез из ТЗ: макет карточки (пилюли категорий → заголовок
→ статус+дата → описание → карта с меткой → магнитуда → источники+ссылка),
карта на живых OSM-тайлах с диск-кешем на бэкенде, все поля EONET Event
из живого API (включая находку, что магнитуда живёт на geometry, не на
событии).

## Что осознанно вне рамок

- **Полный трек/анимация для событий с несколькими точками geometry.**
  Рисуется только последняя позиция — та же точка, что уже используется для
  `event_date`/магнитуды (единообразие с уже принятым в
  `TZ-daily-digest.md` решением «берём последнюю точку»). Трек потребовал
  бы либо более широкого bbox (теряется приближение на текущее положение),
  либо проекции нескольких точек через потенциально разные тайл-сетки —
  заметно больше кода и площадь для ошибок ради decorативной детали.
- **Per-категорийный масштаб карты** (шторм крупнее пожара) — фиксированный
  bbox для всех категорий в этом заходе.
- **GIBS-интеграция** — использован явно предусмотренный ТЗ fallback (OSM);
  переход на GIBS, если понадобится (например, ради спутниковых слоёв,
  которых у OSM нет) — отдельная будущая доработка.
- **Реальная фильтрация по категории на `/earth-events`** — страница сама
  ещё заглушка (`docs/tz/TZ-web.md`); пилюли уже ссылаются на
  `?category=`, сама фильтрация реализуется вместе со страницей.
- **Rate-limiting/платный тайл-провайдер для OSM** — при текущем объёме
  трафика (кеш на бэкенде, один рендер на событие) не требуется; если
  трафик вырастет — заменить `TILE_URL_TEMPLATE` на платный сервис без
  изменений в остальном пайплайне.
