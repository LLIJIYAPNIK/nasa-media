# TZ-web-apod.md — страница APOD: Pinterest-сетка с бесконечной подгрузкой

## Цель

Первая полноценная реализация одного из 6 разделов, под которые сейчас есть
только заглушка (`GET /apod` → `placeholder.html`, см. `docs/tz/TZ-web.md`,
«Вне рамок»). Сетка в духе Pinterest из всех доступных выпусков APOD (NASA
публикует ежедневно без перерыва с 16 июня 1995 года), с бесконечной
подгрузкой вниз, без постраничной навигации. При наведении на тайл — фон
затемняется, появляются описание и кнопка «Читать больше»; если у картинки
есть авторские права — copyright сверху слева, дата съёмки — сверху справа
(дата не зависит от наличия copyright, см. «Решения» ниже). Клик по тайлу или
по «Читать больше» открывает модалку в том же визуальном языке, что и на
главной странице (`<dialog class="detail-modal">`).

Отдельная, явно обозначенная в задаче часть — не бить в NASA API повторно за
одни и те же даты: в проекте уже есть БД (SQLAlchemy/PostgreSQL), поэтому
каждая дата APOD запрашивается у NASA не более одного раза за всё время жизни
проекта, а не при каждом заходе или каждой прокрутке.

## Что уже есть

- `ApodClient.fetch_raw(day) -> ApodData` (`infrastructure/nasa/apod_client.py`)
  — одна дата, один HTTP-запрос к NASA, перевод `title`/`explanation` на
  русский, предпочитает `hdurl`. Уже используется ботом (`ApodProvider`) и
  модалкой карточки APOD на главной (`GetHomepageDetail._apod_detail`). Не
  подходит напрямую для сетки из десятков дат за раз — вызывать его по одному
  разу на дату означало бы N HTTP-запросов к NASA и N пар обращений к
  переводчику на один экран сетки.
- `ApodModel`/`SqlAlchemyApodRepository` (`infrastructure/db/models.py`,
  `infrastructure/db/repositories.py`) — уже существующий кеш APOD в БД, но
  это кеш **пересылки в Telegram admin-chat** (`message_id` обязателен и
  уникален, `file_id` — Telegram file_id), не кеш содержимого APOD.
  Переиспользовать его для веб-сетки не получится и не нужно — это два разных
  факта («это сообщение уже переслано в Telegram» и «эти данные уже получены
  от NASA»), которые сегодня совпадают по ключу (`date`), но по разным
  причинам (см. решение ниже).
- `domain/media/apod_day_count.py` — `APOD_LAUNCH_DATE = date(1995, 6, 16)`,
  уже используется на главной для карточки «день №N». Естественная нижняя
  граница для бесконечной прокрутки: раньше неё запросов к NASA просто не
  будет, и это уже готовая доменная константа, а не новое число.
- `application/digest/ports.py` — `SpaceWeatherClient`/`NearEarthObjectClient`
  уже реализуют `fetch_for_range(start, end)` (добавлено в
  `TZ-weekly-highlights.md`) — устоявшееся в проекте имя метода для «диапазон
  дат одним запросом». Ниже используется то же имя для симметрии, а не
  придумывается новое.
- `presentation/web/static/js/modal.js`, `static/css/modal.css`,
  `homepage.html` — компонент `<dialog class="detail-modal">` с
  шапкой-крестиком и закрытием по клику вне модалки/Esc, именно то модальное
  окно, которое просит переиспользовать задача. В текущем виде `modal.js`
  жёстко завязан на 4 карточки статистики (`[data-kind]` + ленивая загрузка
  `fetch('/api/homepage/details/{kind}')`) — для сетки APOD данные уже есть
  на клиенте (пришли вместе с тайлом), второе обращение к серверу на клик
  было бы лишним. Переиспользуется HTML/CSS `<dialog>`-компонент, но не сам
  `modal.js` (см. решение ниже).
- Фон (звёздное небо + «вихрь Nightreign» из `docs/tz/web-homepage-fixes-round2`)
  уже общий для всех страниц — задан в `layout.css` на `body::before`/`::after`
  и `<canvas class="stars">` в `base.html`, а не в разметке самой главной
  страницы. Разделу APOD для этого ничего добавлять не нужно — важно только
  не переопределять фон `body` в новых стилях.

## Решения по неоднозначностям (с обоснованием)

### Откуда данные и кеш

- **Новая таблица `apod_web_entry`, не переиспользование `ApodModel`.**
  Хранит содержимое APOD по дате: `date` (уникальный ключ), `title`,
  `explanation`, `copyright` (nullable), `image_url` (SD/превью — для
  тайлов сетки), `hdurl` (nullable — для полноразмерной картинки в модалке).
  Отдельная сущность от Telegram-кеша (см. «Что уже есть» выше); если
  когда-нибудь понадобится держать рядом «уже переслано в Telegram» и «уже
  получено от NASA» на одну дату — это два независимых факта в двух
  таблицах, а не одна перегруженная модель на два разных смысла.
- **SD (`url`) и HD (`hdurl`) хранятся раздельно**, в отличие от `ApodData`
  (та схлопывает их в одно поле `image_url = hdurl or url`, это осмысленно
  для одиночной подписи Telegram/модалки главной, где показывается только
  одна картинка). В сетке из десятков тайлов гонять HD-картинки (часто
  несколько мегабайт) на каждый превью-тайл — лишний вес; тайл сетки
  показывает `image_url` (SD), модалка при открытии — `hdurl`, если есть,
  иначе тот же `image_url`.
- **Новый доменный объект `ApodWebEntry`** (`domain/media/entities.py`, рядом
  с `ApodEntry`/`EpicDay`) — чистый dataclass без I/O:
  `date, title, explanation, copyright, image_url, hdurl`.
- **`ApodClient.fetch_for_range(start, end)`** (новый метод в
  `infrastructure/nasa/apod_client.py`, `ApodData`/`fetch_raw` не трогаются)
  — один HTTP-запрос к NASA (`start_date`/`end_date` вместо `date` — NASA
  APOD API официально поддерживает такой запрос и возвращает массив, в
  каждом элементе есть собственное поле `date`) вместо одного запроса на
  каждую дату диапазона. Дни с видео (`media_type != "image"`) молча
  пропускаются — как и в `fetch_raw`, только не бросают исключение на весь
  диапазон: одна дата без картинки не должна валить всю страницу сетки.
  Перевод (`title`/`explanation`) делается только для дат, которых ещё нет в
  БД (решает use-case ниже, см. следующий пункт), с ограниченной
  параллельностью (`asyncio.Semaphore` с небольшим значением, не безлимитный
  `asyncio.gather` по всем датам сразу) — `googletrans` уже отмечен в
  CLAUDE.md как нестабильный (отдельная, не решаемая в этой задаче проблема,
  см. «Вне рамок»), и всплеск в 20–30 параллельных запросов на свежий
  диапазон дат — реалистичный способ столкнуться с этой нестабильностью.
  Если перевод конкретной даты падает — эта дата пропускается в ответе
  (частичная деградация страницы вместо 500 на весь запрос) и не
  сохраняется в БД, чтобы не закешировать порванный текст.
- **Кеш в БД персистентный, не in-memory TTL** — в отличие от `SnapshotCache`
  главной страницы. Там смысл в том, что «данные NASA сегодня» пересчитываются
  раз в 5 минут по определению (см. TZ-web.md, «Кэширование»); APOD за
  прошлую дату не меняется никогда — посчитан один раз, пересчитывать заново
  не нужно ни через TTL-окно, ни после перезапуска процесса. Это буквальное
  прочтение требования задачи «один запрос, скачал, переиспользовал» — один
  раз за всё время жизни проекта на дату, не один раз на TTL-окно.
- **Веб-процесс получает доступ к БД впервые.** Сейчас
  `presentation/web/app.py` вообще не создаёт `engine`/`session_factory` —
  БД использует только бот (`main.py`). Добавляется по тому же образцу:
  `build_engine(config.DB_URL)` → `build_session_factory(engine)` →
  `Base.metadata.create_all` (тот же идемпотентный вызов, что в
  `main.py:105` — так таблица создаётся, даже если веб когда-нибудь запустят
  раньше бота) → `SqlAlchemyApodWebCacheRepository(session_factory)`
  передаётся в use-case веб-галереи.

### Пагинация / бесконечная прокрутка

- **Курсор — дата, не номер страницы.**
  `GET /api/apod/entries?before=YYYY-MM-DD&limit=N` отдаёт до `N` календарных
  дней перед `before` (не включая её), по убыванию даты; без `before` — от
  сегодняшнего дня. Ответ — `{items: [...], next_cursor: "YYYY-MM-DD" | null}`;
  `next_cursor` — самая старая дата в этом окне, передаётся в следующий запрос
  как `before`; `null`, когда окно уже упёрлось в `APOD_LAUNCH_DATE` — фронту
  больше нечего грузить, триггер подгрузки отключается.
- **Окно — календарные дни, не гарантированное число картинок.** Если в окне
  из `N` дней 2–3 дня оказались видео, страница вернёт `N-2`/`N-3` тайлов, а
  не «докручивает» окно, пока не наберёт ровно `N` картинок. Видео у APOD —
  редкость; цикл, который расширяет диапазон ради ровного количества тайлов,
  усложняет use-case ради небольшого визуального нюанса. Если на живых данных
  сетка будет заметно «скакать» по плотности — дорабатывается отдельно, не
  здесь.
- **Подгрузка на фронте — `IntersectionObserver` на сторожевом элементе в
  конце сетки**, без сторонней библиотеки (vanilla JS — тот же вкус, что и у
  остального веба, см. TZ-web.md, «Выбор стека»): сторожевой элемент попадает
  в вьюпорт → `fetch` следующей страницы текущим `next_cursor` → тайлы
  добавляются в DOM → `next_cursor` обновляется; когда он `null` —
  `observer.disconnect()`.
- **Первая страница — серверный рендеринг** (Jinja2, как и главная страница),
  а не пустой `<div>` и JS-запрос сразу после загрузки — та же причина, что
  на главной: страница осмысленна и без JS (TZ-web.md). `limit` первой
  страницы — одна и та же константа для серверного рендера и для клиентских
  догрузок: шаблон прокидывает её в разметку (`data-limit` на контейнере
  сетки), `apod_gallery.js` читает оттуда, а не хранит число отдельно — чтобы
  значение не разъехалось между Python и JS.

### Вёрстка сетки

- **CSS-колонки (`column-count` + `break-inside: avoid`), не JS-библиотека
  раскладки и не `grid` с измерением высоты картинок.** Даёт визуальный
  эффект Pinterest (тайлы разной высоты, плотная упаковка) без сторонней
  библиотеки и без JS-кода, который замерял бы загруженные картинки, чтобы
  проставить `grid-row-end` — самый дешёвый вариант, отвечающий духу
  «vanilla JS, без лишних инструментов» (TZ-web.md). Плата за простоту —
  порядок обхода тайлов колоночный (сверху вниз, потом следующая колонка), не
  единым рядом слева направо по дате; для медиа-сетки, где основной сценарий
  — визуальный скролл, а не чтение строго по порядку дат, это приемлемо.
- **Оверлей по `:hover`/`:focus-within`** (не только `:hover` — чтобы
  тайлы были доступны с клавиатуры без мыши): затемнение градиентом поверх
  картинки, обрезанное по высоте описание (`-webkit-line-clamp`; `explanation`
  и так не длиннее 512 символов после перевода, см. `APOD_MAX_DESCRIPTION_LENGTH`
  в `apod_client.py`) и кнопка «Читать больше» (класс `.btn-glass`, как на
  главной). **Дата — всегда** в правом верхнем углу оверлея: без даты тайл
  бесполезен для навигации по сетке, в этом весь смысл раздела. **Copyright —
  в левом верхнем углу, только если есть** — тот же опциональный паттерн, что
  уже используется в `renderApod`/`build_apod_caption` (`TZ-copyright.md`):
  не каждая картинка чужая, у большинства copyright просто нет.
- **Модалка по клику на тайл или на «Читать больше»** — тот же
  `<dialog class="detail-modal">`, что на главной (переиспользуется разметка
  и стили `modal.css`), но контент берётся не через
  `fetch('/api/homepage/details/...')`, а напрямую из данных тайла, уже
  лежащих в памяти страницы (`Map` по дате, заполняется по мере добавления
  тайлов в сетку) — второго обращения к серверу на клик не требуется, ровно
  то, что просит задача. В модалке — HD-картинка (`hdurl`, если есть, иначе
  `image_url`), полный (без `line-clamp`) текст описания, copyright, дата.
- **Отдельный, новый `apod_gallery.js`, не правка `modal.js`.** `modal.js`
  жёстко заточен под 4 фиксированных `kind` со своей моделью ленивой
  подгрузки по сети (см. «Что уже есть»); совмещать в одном файле «подгрузка
  по клику по сети» и «рендер из уже загруженных данных» ради одного нового
  вызывающего места добавило бы ветвление в и так небольшой файл — отдельный
  маленький модуль читается проще. HTML/CSS самого `<dialog>` переиспользуются
  как есть, без дублирования стилей.

## Роуты

- `GET /apod` — заменяет заглушку: ключ `/apod` убирается из
  `PLACEHOLDER_SECTIONS` (`presentation/web/routers/homepage_router.py`).
  Рендерит `apod.html`: общий нав-рейл (из `base.html`), сетка с первой
  страницей (`page_size` тайлов от сегодняшней даты), сторожевой элемент для
  подгрузки, модалка.
- `GET /api/apod/entries?before=&limit=` — JSON-страница для подгрузки (см.
  «Пагинация» выше). `limit` необязателен, по умолчанию — тот же `page_size`,
  что и у первого серверного рендера.

## Что осознанно вне рамок

- **Пиксель-точные значения сетки** (число колонок на брейкпоинт, отступы,
  радиус тайла, число строк в обрезанном описании) — как и в TZ-web.md,
  отдельного макета в Claude Design под этот раздел нет; значения подбираются
  по месту при вёрстке и, при необходимости, уточняются отдельным раундом
  правок (`docs/tz/web-apod-fixes/`), по той же схеме, что и главная
  страница, а не фиксируются здесь числами.
- **Починка нестабильности `googletrans`** — известная отдельная проблема
  (CLAUDE.md, «Вне текущего скоупа»); эта задача только ограничивает
  параллельность запросов к переводчику и деградирует по отдельной дате при
  ошибке, не переписывает сам механизм перевода.
- **Заблаговременный прогрев кеша** (фоновая задача, которая заранее
  скачивает и переводит все даты с 1995 года) — не делается; кеш наполняется
  лениво, по мере того как посетители реально доскроллили до соответствующих
  дат. Если понадобится настоящий прогрев — отдельная задача (разовый
  скрипт/management-команда), не часть этой ТЗ.
- **Фильтр или поиск по сетке** (по дате, по наличию copyright и т.п.) — не
  запрашивался, не добавляется.
- **Видео-выпуски APOD** — по-прежнему не показываются нигде в проекте (см.
  `fetch_raw`), сетка тоже только про изображения; отдельная обработка
  video-дней (например, embed) не входит в задачу.
- **EPIC и остальные разделы** — по-прежнему заглушки, этой задачей не
  трогаются (см. TZ-web.md).

## Отклонения от ТЗ при реализации

- **`GetApodGalleryPage.execute(before, today)` получил третий необязательный
  параметр `page_size`.** В «Целевых файлах» сигнатура — `execute(before,
  today)`, но роут `GET /api/apod/entries?limit=` не может честно уважать
  клиентский `limit` без этого — иначе принятое значение либо ни на что не
  влияет (мёртвый параметр), либо `GetApodGalleryPage` пришлось бы
  пересоздавать на каждый запрос, ломая DI-конвенцию, общую с
  `build_homepage_router` (use-case собирается один раз в `app.py`, не в
  роуте). Параметр опционален и по умолчанию берёт `page_size`, заданный в
  конструкторе — вызовы `execute(before, today)` без изменений ведут себя
  как описано в ТЗ, все перечисленные тесты (кроме `limit`) проходят как есть.
- **Тестовый файл веб-роута APOD называется `test_web_apod_router.py`, не
  `test_apod_router.py`.** ТЗ называет его тёзкой
  `presentation/telegram/routers/apod_router.py` — «не конфликтует по пути
  импорта» верно для модулей под тестом, но `tests/presentation/` плоский
  (без под-пакетов `telegram`/`web`), и `test_apod_router.py` там уже занят
  тестами Telegram-роутера (`presentation/telegram/routers/apod_router.py`,
  см. `tests/presentation/test_apod_router.py`). Пришлось переименовать во
  избежание коллизии путей на уровне файловой системы.
