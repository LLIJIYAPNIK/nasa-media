# CLAUDE.md — nasa-media (Telegram-бот)

Инструкция для Claude Code по доработке проекта. Изначально бот был сделан
~2 года назад как дипломная работа Skillbox (репозиторий
`NasaAPI-bot-skillbox-diploma`); сейчас функционал переносится в новый
репозиторий `nasa-media` с актуализированной архитектурой. Не выдумывай факты и
решения, которых здесь нет — если чего-то не хватает, оставляй заметный `TODO:`
в коде и спрашивай, а не додумывай сам.

## Статус проекта и репозиторий

Telegram-бот на `aiogram 3`, два источника контента от NASA — APOD (картинка дня)
и EPIC (снимки Земли), хранилище — PostgreSQL через SQLAlchemy 2.0 async.
В `nasa-media` уже есть тесты по каждому слою и CI (GitHub Actions: тесты,
типы, форматирование) — этого не было в унаследованном коде старого репозитория.

Разработка ведётся в новом репозитории **`nasa-media`** — старый код в
`NasaAPI-bot-skillbox-diploma` не дорабатывается. Причины переноса: старое
название и описание завязаны на бренд Skillbox (курс, который автор не хочет
рекламировать в своём профиле), плюс накопленный технический долг (см. «Известные
ошибки» ниже) проще перенести осмысленно, чем чистить на живую в старой истории
коммитов.

- Старый репозиторий (`NasaAPI-bot-skillbox-diploma`) остаётся публичным как
  ссылка на первую версию/происхождение проекта — README нового репозитория
  должен на него ссылаться.
- Когда основной функционал (5 пунктов ниже) реализован в `nasa-media` — старый
  репозиторий переводится в архив на GitHub. Раньше времени не архивировать.
- Лицензия — **MIT** (файл `LICENSE` в корне нового репозитория, автор указан как
  Alexander Kulebyakin). Выбрана для единообразия с остальными репозиториями
  профиля (уже используется в `Configuration-management-RTU-MIREA-...`) и
  потому что ни одна из зависимостей проекта не требует copyleft. Лицензия
  покрывает только код бота — данные NASA остаются public domain по политике
  NASA независимо от лицензии репозитория.

В долгосрочных планах — веб-интерфейс, платформа для доступа ко всем API NASA
(не только APOD/EPIC, которые сейчас есть в боте). Веб живёт **в этом же
репозитории** `nasa-media`, а не в отдельном — по аналогии с проектом
a-kulebyakin.ru, где статический сайт, Telegram-бот и веб-админка тоже
работают над одним общим бэкендом в одном репозитории. Практическое следствие:
DDD-слои `domain`/`application`/`infrastructure` должны оставаться независимыми
от конкретной presentation-поверхности, чтобы веб в будущем переиспользовал их,
а не дублировал (см. «Соблюдение DDD» ниже) — `presentation/telegram` уже
сейчас, `presentation/web` появится позже. Веб-часть потребует своего
`TZ-web.md`, когда до неё дойдёт очередь. **Сейчас веб вне скоупа** — делаем
только бота, но архитектура заранее не должна закрывать на него дверь.

## Безопасность и секреты (репозиторий публичный)

`nasa-media` — публичный репозиторий с самого первого коммита, не приватный
с последующим открытием. Значит, дисциплина по секретам нужна не «когда-нибудь
почистим», а с нулевого коммита — по факту утечки из истории git убрать
практически невозможно (перезапись истории на публичном репозитории не спасает,
если кто-то уже склонировал).

- `.env` — в `.gitignore` с первого коммита, реальные значения `BOT_TOKEN`,
  `NASA_API_KEY`, `DB_URL`, `ADMIN_CHAT_ID` никогда не попадают в git.
- Вместо реальных значений — `.env.example` с плейсхолдерами
  (`BOT_TOKEN=your_bot_token_here` и т.п.), README ссылается на него, а не
  показывает пример с настоящим ключом «для наглядности».
- Никаких секретов в коде, комментариях, тестовых фикстурах, docker-compose/CI
  конфигах — даже временно «чтобы быстро проверить и потом убрать». Убрать
  «потом» не успевают.
- Перед первым пушем нового репозитория и перед каждым `git push` в целом —
  проверять `git diff --staged` на случайно застрявшие ключи/токены/URL с
  паролем. Если есть возможность — включить сканер секретов (например
  `gitleaks`) как pre-commit хук или шаг CI, раз репозиторий публичный.
- `DB_URL` в формате из README (`postgresql+asyncpg://user:pass@host:port/db`)
  содержит пароль в самой строке — при документировании конфигурации в новом
  репозитории показывать только шаблон с плейсхолдерами, не реальную строку
  подключения ни в каком виде.
- Если секрет всё же случайно закоммичен в публичный репозиторий — считать его
  скомпрометированным сразу и ротировать (перевыпустить токен/ключ), а не
  просто удалять коммit задним числом.

## Управление зависимостями (uv)

Зависимости управляются через **`uv`** (Astral), а не голый `pip install -r
requirements.txt` — так же, как в остальных Python-репозиториях автора
(`the-bunker-game`, `Configuration-management-RTU-MIREA-...`), для единообразия
по профилю.

- `pyproject.toml` — единственный источник списка зависимостей, `uv.lock`
  коммитится в репозиторий для воспроизводимых сборок. Старый `requirements.txt`
  не переносится как есть — зависимости перечисляются заново по факту
  используемых импортов.
- Заодно закрывает два известных бага из старого репозитория (см. «Известные
  ошибки», п. 2): `requirements.txt` был сохранён в UTF-16, и в нём висели
  неиспользуемые `tortoise-orm`/`pypika-tortoise` — при ручном пересоздании
  списка зависимостей это не переносится.
- Установка — `uv sync`, запуск бота — `uv run python main.py` (или актуальный
  entry point после DDD-рефакторинга). README документирует именно эти команды.
- CI (`.github/workflows/ci.yml`) тоже через `uv` (`uv sync --locked`, затем
  `uv run ruff/mypy/pytest`), не через голый `pip`, для консистентности с
  локальной разработкой.

## Инженерные принципы

- **DDD / Clean Architecture.** Целевая раскладка: `domain` — чистые правила без
  I/O (например: «дата APOD не может быть раньше `APOD_LOWER_BOUND`», «пользователь
  подписан или нет»), `application` — сценарии use-case («отдать APOD за дату»,
  «подписать пользователя на рассылку», «собрать таймлапс EPIC за сутки»),
  `infrastructure` — реализация портов (HTTP-клиент NASA, SQLAlchemy-репозитории,
  отправка в Telegram, сборка GIF/файловые операции), `presentation` — aiogram
  роутеры и хендлеры, тонкие: разбор апдейта и вызов application-слоя, без
  бизнес-логики внутри хендлера.
- **Не дублировать код.** `APOD` и `EPIC` сейчас реализованы почти зеркально —
  свой `handler`, свой `tools/sender`, свой `fill_db`/аналог. Это тот же паттерн
  долга, что уже случился в другом проекте автора (см. сайт a-kulebyakin.ru,
  `TZ-anime-games-shared-refactor.md` — показательный пример того, чего не надо
  повторять). При переходе на DDD-слои общая часть APOD/EPIC (получить медиа по
  дате → закешировать через admin-chat → отдать пользователю → управлять
  подпиской) выносится в общий `application`/`domain` слой один раз, а не
  копируется в третий раз при добавлении новых источников (Mars Rover Photos,
  NeoWs и т.п. из бэклога идей).
- **Перед нетривиальной фичей — короткое ТЗ** (`docs/tz/TZ-<тема>.md`):
  цель, решения по неоднозначностям с обоснованием, что реализовано, что осознанно
  вне рамок. Обязательно для новой фичи или изменения архитектуры; необязательно
  для мелких багфиксов.
- **Один источник правды на факт.** Список известных багов и решений по фичам —
  здесь и в соответствующих `docs/tz/TZ-*.md`, не размазывать по комментариям в
  коде и чатам.

## Процесс работы (git-flow)

- **Ветка на фичу.** Каждый из 5 пунктов ниже (и любая фича вообще) — отдельная
  ветка, никогда напрямую в `main`. По готовности — Pull Request, даже если
  ревьюер один и тот же человек: PR фиксирует границу фичи и даёт место для
  диффа/чеклиста, а не только для истории коммитов.
- **Маленькие коммиты, строго по фиче.** Один коммит — одно законченное
  логическое изменение. Не смешивать в одном коммите фичу, рефакторинг и
  багфикс, даже если они рядом по месту в коде — это разные коммиты, даже в
  одной ветке.
- **Рефакторинг — обязательный шаг после блока.** Фича не считается
  завершённой сразу после того, как заработала: после реализации — отдельный
  проход на дублирование, длину функций, соответствие DDD-слоям, и только
  затем PR. Рефакторинг такой фичи — отдельный(ые) коммит(ы) поверх «сделал
  фичу», не смешивать с самой фичей в одном коммите.
- **Тесты обязательны всегда**, не «когда-нибудь потом» — каждая фича
  покрывается тестами до PR, а не после. Это отменяет более ранний пункт
  «тестов пока нет» — из статуса проекта он про унаследованный код старого
  репозитория, а не про целевой процесс в `nasa-media`.
- **Не дублировать код** — см. «Инженерные принципы» ниже, это касается и
  новых фич: прежде чем копировать блок кода на соседний сценарий (например,
  вторая подписка, второй источник медиа), сначала проверить, не выносится ли
  он в общий слой.

## Текущий фокус (5 пунктов)

### 1. GIF/таймлапс для EPIC

EPIC отдаёт по несколько кадров Земли за сутки (эндпоинт вида
`.../natural/date/{date}`, список кадров с таймстампами). Задача — скачать все
кадры за дату, собрать в анимацию (GIF или короткое видео), закешировать по тому
же паттерну, что и одиночные фото (через admin-chat, `message_id` в БД). Не
задание на новый API-запрос за каждый кадр отдельно от пользователя — сборка
происходит один раз на дату, дальше раздаётся как обычно.

### 2. Известные ошибки (перевод не трогаем)

Зафиксированные при разборе проблемы, не связанные с переводом:

- `AsyncIOScheduler` создаётся в `main.py`, но нигде не запускается и не
  используется — реальный цикл обновлений сделан вручную через `asyncio.sleep` в
  `aiogram_run.py`. Либо использовать APScheduler по назначению, либо убрать
  мёртвый импорт и саму зависимость.
- `tortoise-orm` и `pypika-tortoise` в `requirements.txt` нигде не импортируются —
  весь проект на SQLAlchemy. Убрать неиспользуемые зависимости.
- `current_date()` в `handlers/APOD/tools/await_date_data.py` делает синхронный
  `requests.get` внутри async-функции — блокирует event loop. Переписать на
  `aiohttp` (он уже есть в зависимостях и используется рядом же для скачивания
  картинок).
- `temp_image_path = "temp_image.jpg"` — общее фиксированное имя файла без
  уникального суффикса. При параллельных запросах два пользователя могут
  перезаписать файл друг друга. Заменить на уникальное имя (`uuid4` или
  `chat_id + timestamp`).
- `except Exception` вокруг `bot.send_photo` в `await_date_data.py` слишком
  широкий — маскирует любые ошибки, а не только «прямая ссылка не открылась».
  Сузить до конкретных сетевых/API-ошибок.
- `requirements.txt` был сохранён в UTF-16 — в новом репозитории не актуально:
  зависимости переезжают в `pyproject.toml`/`uv.lock` (см. «Управление
  зависимостями» выше), `requirements.txt` не переносится.

### 3. День рождения для APOD

- Добавить пользователю поле даты рождения (новая колонка в `Users`), запрашивать
  один раз через отдельную кнопку/сценарий FSM, а не при каждом `/start`.
- Разовый режим: кнопка «узнать свой космический день рождения» — по сути
  переиспользует уже существующий сценарий «определённая дата», просто с другой
  подписью.
- Проактивный режим: раз в год, по совпадению месяца и дня (не года), в
  существующем суточном цикле (`periodic_update_dates`) добавить проход по
  пользователям с сегодняшним днём рождения и отправку персонального
  поздравления с APOD-картинкой. Переиспользует существующий кеш через
  admin-chat — повторного скачивания/перевода не требует.
- Подпись сообщения должна давать повод переслать/поделиться (упоминание бота) —
  это единственный бесплатный канал роста, который у бота пока не задействован.

### 4. Авторские права

- В ответе APOD API есть необязательное поле `copyright` — если оно присутствует,
  значит изображение НЕ в общественном достоянии, это работа стороннего
  астрофотографа, показанная NASA с разрешения. Сейчас код это поле не
  проверяет и не выводит.
- При наличии `copyright` — добавлять в подпись сообщения атрибуцию автора
  (например: `© {copyright}`), не подписывать такие картинки просто как «NASA».
- Поле не обязательно хранить в БД отдельно — кеш и так работает через
  `message_id`, достаточно учитывать `copyright` на этапе формирования подписи
  перед первой отправкой в admin-chat.

### 5. Соблюдение DDD

- Зафиксировать в отдельном `TZ-ddd-refactor.md` целевые сущности и use-case'ы
  до начала переноса кода — не разбирать архитектуру по ходу дела вслепую.
- Явно выделить общий слой для APOD/EPIC (и задела под будущие источники из
  бэклога идей — Mars Rover Photos, NeoWs, DONKI и т.п.): «получить медиа по
  дате», «закешировать через admin-chat», «управлять подпиской пользователя» —
  это не должно жить в двух копиях.
- Роутеры (`apod_handler.py`, `epic_handler.py`, `start_handler.py`) остаются
  тонкими — вызывают application-сервисы, не содержат прямых обращений к
  `requests`/`aiohttp`/файловой системе.
- Presentation-слой раскладывается с заделом на будущий веб: `presentation/telegram`
  для текущих aiogram-роутеров, чтобы `presentation/web` (когда до него дойдёт
  очередь) подключался к тем же `application`-сервисам, не трогая и не
  дублируя domain/application/infrastructure.

## Вне текущего скоупа (осознанно)

- Переработка перевода (сейчас `googletrans`, известная его нестабильность) —
  отдельная задача, не в рамках текущих 5 пунктов.
- Структурированное логирование — желаемое на будущее, но не часть текущего
  захода.
- CI (GitHub Actions, `.github/workflows/ci.yml`) уже настроен: `uv sync
  --locked`, `ruff check`, `ruff format --check`, `mypy`, `pytest` на каждый
  push в `main` и на каждый PR. Это больше не вне скоупа — пункт оставлен
  здесь как история: раньше CI был сознательно отложен, потом запрошен
  отдельно и сделан вне порядка 5 пунктов «текущего фокуса».
- Веб-интерфейс доступа ко всем API NASA — часть того же репозитория `nasa-media`,
  но следующий этап работ, свой `TZ-web.md`; сейчас не проектируется и не
  реализуется, только не блокируется архитектурно (см. «Статус проекта» выше).
